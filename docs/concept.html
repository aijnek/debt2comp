debt2comp — concept v2

理解負債の返済設計

AIがコードを書き、自分が上流設計とハーネスに回ると、動いているシステムに対する理解だけが取り残される。 これを「読み物を配って終わり」にせず、検証可能な主張（claim）を単位として、抽出・検証・学習・出題・記録を一つの環に閉じるための設計メモ。 まず自分一人の理解負債を返す道具として作り、チーム共有は将来の拡張として線だけ引いておく。

core unit

すべての単位を claim に揃える

理解度を「セキュリティ 70%」のようなトピック粒度で持つと、次に何を見せればいいかが決まらない。 代わりに、コードに紐付いた検証可能な一文を最小単位にする。 こうすると教材・出題・記録・陳腐化検出のすべてが同じIDで回る。

claim には型を持たせる。 invariant（成り立ち続けるべき性質）、 decision（なぜこの形かという判断）、 dataflow（データがどう流れるか）、 failure（どう壊れうるか）、 convention（このリポジトリの約束事）。 型は飾りではなく、出題形式（不変条件なら反例探し、データフローなら経路当て）と検証手段の選択を決める入力になる。

CLAIM · auth-004 invariant verified intent: inferred
外部公開されるルートは全て middleware/auth.py の require_auth を通る。これを迂回する登録経路は存在しない。
anchors middleware/auth.py :: require_auth
routes/__init__.py :: register_all
verify scripts/audit_routes.py --public --without require_auth → 0件
last pass 2026-08-29 @ 9f2c1ab
intent 認可判定を1箇所に集約し、ルート追加時の付け忘れを構造的に防ぐため
topic security

意図は記録されていないことのほうが多い。だからエージェントには推論を許すかわりに出所ラベルを必須にする。 recorded は PR やADRに実在する記述、 inferred はコードからの推定、 unknown は根拠なし。 推定を事実として教えないことが、この仕組みが嘘を教えないための防波堤の一つになる。

意図が unknown のまま残った重要claimの一覧は、それ自体が成果物になる。「誰も理由を知らないまま動いている場所」の地図だ。

verification

claim に検証手続きを添付する

v1 の最大の弱点は、claim の品質下限と鮮度の両方がエージェントの善意に預けられていたことだった。 v2 ではこれを一つの仕組みで塞ぐ。抽出時にエージェントは、可能な限り機械的な検証手続き（grep・スクリプト・テスト参照）を claim に添付し、その場で実行して裏を取る。

検証手続きを持ち実行に通った claim は verified、 書けなかったものは asserted とラベルする。 意図の recorded / inferred が「意図の信頼性」の防波堤であるのと同型に、これは「事実の信頼性」の防波堤になる。 効果は二重で：

品質下限 — もっともらしく間違った claim は、verify を書こうとした時点で大半が露見する。 承認ゲートを置かない方針は維持したまま、疑いの主戦場が asserted だけに絞られる。 asserted の比率そのものを claim 集合の品質指標として表示する。

陳腐化検出の格上げ — verified な claim は、SHA 比較（変わったかもしれない）ではなく再実行（今も真か）で検査できる。 アンカー先が変わっても verify が通れば claim は生きている。stale の大半が誤検知ごと消える。 asserted な claim だけがアンカー照合のフォールバックに残る。

既存テストは「真であってほしいと明文化された一文」そのものなので、最初の verified claim の供給源として収穫する。 「怪しい」ボタンは、押すとエージェントの再検証タスク（verify の再実行、反例探し）が走り、訂正または棄却が訂正履歴に記録される——ここまでを含めて一つのフローとして定義する。

entry

入口は順序ではなく、地図

学習の完了基準も順序も定義しない方針は維持する。ただし数百の claim を前にトピック一覧だけ渡されても入れない。 そこで抽出時に、claim 集合の最上位にオリエンテーションを生成する。 システム全体のアーキテクチャ、モジュールの責務、主要なデータの流れ、貫かれている設計思想を一枚の読み物＋図として書き、 すべての要素からトピックと claim へリンクを張る。 メンタルモデルの骨格を先に渡し、気になった場所から深掘りできるようにする。順序は与えないが、地図は与える。

ブラウザ側の体験は四つの面で構成する。

01 · 入口
オリエンテーション地図
アーキテクチャと設計思想の全体像。各モジュール・フローから該当トピックと claim 群へ降りられる。学習カバレッジと採掘カバレッジもここに重ねて表示する。
02 · 閲覧
コード × claim オーバーレイ
実コードの上に claim カードが浮かぶ閲覧モード。「場所を特定できる」ゴールの土台であり、場所当て問題の出題面も兼ねる。
03 · 教材
実行経路ツアー
リクエストや処理がコードを流れる様子をステップ実行風に辿る。claim が経路上の該当箇所で現れ、ばらばらの事実が一本の線になる。
04 · 定着
出題セッション
1問ずつのテンポ、即時フィードバック、誤答時の丁寧な解説。正誤とは独立に「このclaimは怪しい」を常設する。
storage

資産と現在地を分けて置く

ソロ運用でも二層に分ける。claim 集合はリポジトリから採掘した資産なのでコミットして履歴管理する。 学習状態は自分の現在地であって、リポジトリの歴史に混ぜるノイズになるので gitignore する。 将来チームで使うなら、この線がそのまま共有境界になる（採掘コストを払うのは一人、全員がその上に乗る）。

committed · 資産
.comprehension/
  • claim集合（本文・型・アンカー・verify・意図・出所ラベル）
  • オリエンテーション（地図・設計思想）
  • トピック定義と claim の所属
  • 問題プール（claim × 難易度 × 形式）
  • 訂正履歴（いつ何をなぜ直したか）
gitignored · 現在地
.learning/
  • claim ID → 状態 unseen / learned / stale / invalidated / orphaned
  • 学習した時点の commit SHA
  • 出題と正誤の履歴

状態を分けるのは、「古びた」と「間違っていた」を区別する必要があるから。 verify が落ちるかアンカー先が変われば stale（内容は正しかったが現状と合わない可能性）、 claim 本文が訂正されれば invalidated（学んだ内容自体が誤りだった）、 アンカー先のコードが消えれば orphaned（claim の対象自体が消滅した可能性）。 それぞれ再学習の意味が違う。

loop

体験の一周

抽出・執筆・記述採点はエージェント、出題の進行と採点の大半はコード。 v1 では全問がエージェント往復だったが、v2 では問題プールを事前生成し、適応ロジックをサーバ側の決定的ポリシーに移す。 エージェントのターンが要るのは同期・記述採点・再検証だけになり、出題中の待ち時間がほぼ消える。

  1. agent · 初回のみ 全体を一度だけ重く抽出する リポジトリ全体を走査してトピック・claim集合・verify手続き・オリエンテーション・問題プールを作り切り、実行できるverifyは全て実行して裏を取ってからコミットする。
  2. agent · 起動時 差分を同期する 前回からのコード差分を検査し、影響を受けた claim の verify を再実行、壊れたものを訂正または stale/orphaned に落とし、新しい領域から claim を追加抽出し、オリエンテーションと問題プールを追随させる。学ぶ直前に必ず鮮度が揃う。
  3. human 地図から入る オリエンテーションで全体像を掴み、気になった領域を選ぶ。どこまでやれば終わりかは定義しない。二軸のカバレッジが見えていれば、次に進むかどうかは本人が決められる。
  4. browser 教材で線をつくる claimカード（何が成り立っているか）、実行経路ツアー（どう繋がるか）、経緯（なぜ今の形か、git履歴から）、コードオーバーレイ（どこにあるか）。
  5. code プールから適応的に出題する 正答なら深く・隣へ、誤答なら同じclaimを別の角度で。ポリシーは決定的で、選択式・場所当ては即採点。エージェント往復が要るのは記述回答の採点だけで、それも非同期でよい。
  6. code .learning に書き戻す 状態・SHA・正誤履歴を更新し、二軸カバレッジを再計算する。次回起動時の出発点になる。
coverage

カバレッジは二軸で見せる

推定理解度は出さない方針を維持しつつ、根拠が明確な数字だけを二つ見せる。 学習カバレッジ（学習済み claim ÷ 全 claim）は自分の進み、 採掘カバレッジ（1つ以上の claim にアンカーされたコード ÷ 全コード）は claim 集合そのものの網羅を示す。

v1 の open issue「カバレッジ100%でも抽出漏れは見えない」への答えがこの第二軸になる。 分母の外に消えていた un-claimed 領域が、「誰も何も主張していないディレクトリ」としてオリエンテーション地図の上に可視化される。 満点の画面の裏に消える領域をなくす。

responsibility

コードが決めること、エージェントが決めること

判断はSkillを発動しているエージェントの能力で行い、LLM APIは呼ばない。 だからこそ、ぶれてはいけないものは全部コード側に置く。

層担うものそこに置く理由
Python claim / 学習ログのスキーマと読み書き、verify の実行と結果判定、アンカー照合、差分検出、ローカルサーバとUI描画、二軸カバレッジ集計、プールからの出題ポリシー、選択式・場所当ての即採点 正解が確定しているものと、実行のたびに変わってはいけないもの。ここが決定的なら、エージェントの出力がぶれても記録は壊れない。
Agent claim の抽出と型付け、verify 手続きの設計、意図の推定と出所判定、オリエンテーションと教材の執筆、問題プールの生成、記述回答の採点、「怪しい」への再検証と訂正 コードを読んで意味を汲む必要があるもの。ここは毎回違ってよく、違うほうが学習体験としては良い。

open

未解決として残っているもの

verify 自体の品質は、誰も検証しない
緩すぎる verify（常に通る grep）は偽の verified を作り、v1 の「もっともらしく間違った claim」より質の悪い安心を生む。 verify は claim の正しさの証明ではなく反証機会の確保でしかない、という位置づけを UI 上でも崩さないこと。 抽出時に「この verify は claim が偽なら本当に落ちるか」をエージェントに自問させる手順を Skill 側に書く。
asserted な claim の品質下限は依然として薄い
verify を書けなかった claim（設計判断・慣習に多い）は「怪しい」ボタン頼みのまま。 asserted 比率を品質指標として見せることと、出題時に asserted であることを学習者に明示することで、疑う余地を残す。
オリエンテーションの鮮度は claim のように検査できない
地図はアンカーも verify も持たない散文なので、陳腐化を機械的に検出できない。 起動時同期でエージェントが書き直す運用だが、差分が地図の記述に影響するかの判定自体がエージェント任せになる。 地図の各節に「依拠している claim ID」を持たせ、それらが stale になったら節を要更新とする、が次の一手の候補。
採掘カバレッジは「浅い網羅」を隠す
ファイルに1つでも claim があれば分子に入るため、重要な性質が抜けたまま網羅済みに見える。 アンカーの有無は見えるようになったが、アンカー済み領域の中の抽出漏れは依然として見えない。
問題プールの使い回しは記憶ゲーになる
同じ問題の再出題は claim の理解ではなく答えの記憶を測ってしまう。 プールに claim ごとの問題数の下限を置く、正答済み問題は同一 claim の別問題を優先する、枯渇したら次回同期で補充する、あたりの契約が要る。
忘却は明示的に先送りした
陳腐化はコード変更で検出できるが、コードが変わらなくても人は忘れる。 正誤履歴は記録しているので、間隔反復を後から足す余地は残っている。定期実行の検討と一緒に決める。
