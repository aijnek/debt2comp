debt2comp — concept

理解負債の返済設計

AIがコードを書き、人間が上流設計とハーネスに回ると、動いているシステムに対する理解だけが取り残される。 これを「読み物を配って終わり」にせず、検証可能な主張（claim）を単位として、抽出・学習・出題・記録・訂正を一つの環に閉じるための設計メモ。

core unit

すべての単位を claim に揃える

理解度を「セキュリティ 70%」のようなトピック粒度で持つと、次に何を見せればいいかが決まらない。 代わりに、コードに紐付いた検証可能な一文を最小単位にする。 こうすると教材・出題・記録・陳腐化検出のすべてが同じIDで回る。

CLAIM · auth-004 intent: inferred
外部公開されるルートは全て middleware/auth.py の require_auth を通る。これを迂回する登録経路は存在しない。
anchors middleware/auth.py :: require_auth
routes/__init__.py :: register_all
at sha 9f2c1ab
intent 認可判定を1箇所に集約し、ルート追加時の付け忘れを構造的に防ぐため
topic security

意図は記録されていないことのほうが多い。だからエージェントには推論を許すかわりに出所ラベルを必須にする。 recorded は PR やADRに実在する記述、 inferred はコードからの推定、 unknown は根拠なし。 推定を事実として教えないことが、この仕組みが嘘を教えないための唯一の防波堤になる。

意図が unknown のまま残った重要claimの一覧は、それ自体が成果物になる。「誰も理由を知らないまま動いている場所」の地図だ。

storage

知識は共有し、理解度は個人に閉じる

claim集合はリポジトリから採掘したチームの資産なので、コミットして共有する。 誰が何をわかっているかは評価につながるので、個人の手元に閉じる。この分割で、新メンバーは採掘コストを払わずに初日から学習に入れる。

committed · 共有
.comprehension/
  • claim集合（本文・アンカー・意図・出所ラベル）
  • トピック定義と claim の所属
  • 訂正履歴（誰がいつ何を直したか）
gitignored · 個人
.learning/
  • claim ID → 状態 unseen / learned / stale / invalidated
  • 学習した時点の commit SHA
  • 出題と正誤の履歴

状態を分けたのは、「古びた」と「間違っていた」を区別する必要があるから。 アンカー先のコードが変われば stale（内容は正しかったが現状と合わない可能性）、 claimが訂正されれば invalidated（学んだ内容自体が誤りだった）。 後者は訂正した本人だけでなく、そのclaimを学習済みにしている全員に伝播する。

loop

体験の一周

採点も抽出もエージェント自身が行う。ローカルサーバはLLMを持たない状態の受け渡し口であり、 この仕組みは本質的にターン制になる。

  1. agent · 初回のみ 全体を一度だけ重く抽出する リポジトリ全体を走査してトピックと claim集合を作り切り、コミットする。以降は差分更新のみ。一人が一度払えば、チーム全員がその上に乗る。
  2. code 起動時に陳腐化を検査する 学習済みclaimのアンカー先が学習時のSHAから変更されていないかを機械的に照合し、変わっていれば stale に落とす。トピック一覧はカバレッジ付きで提示する。推定理解度は出さない。
  3. human 深めたい領域を選ぶ どこまでやれば終わりかは定義しない。カバレッジと理解度が見えていれば、次に進むかどうかは本人が決められる。
  4. agent → browser 教材を三つの形で書く claimカードの集まり（何が成り立っているか）、実行経路のツアー（それがどう繋がるか）、なぜ今の形なのかの経緯（git履歴から）。ばらばらの事実ではなく一本の線になるように。
  5. browser ⇄ agent 1問ずつ出題し、採点して次を選ぶ 選択式・場所当て・記述の混合。正誤とは独立に「このclaimは怪しい」を常設し、承認ゲートを置かない代わりの訂正の入口にする。
  6. code .learning に書き戻す 状態・SHA・正誤履歴を更新し、カバレッジを再計算する。次回起動時の出発点になる。
responsibility

コードが決めること、エージェントが決めること

判断はSkillを発動しているエージェントの能力で行い、LLM APIは呼ばない。 だからこそ、ぶれてはいけないものは全部コード側に置く。

層担うものそこに置く理由
Python claim / 学習ログのスキーマと読み書き、ローカルサーバ、HTML描画、アンカー変更の検出、カバレッジ集計、選択式と場所当ての即採点 正解が確定しているものと、実行のたびに変わってはいけないもの。ここが決定的なら、エージェントの出力がぶれても記録は壊れない。
Agent claim抽出、意図の推定と出所判定、教材の執筆、問題の生成、記述回答の採点、claim訂正の反映 コードを読んで意味を汲む必要があるもの。ここは毎回違ってよく、違うほうが学習体験としては良い。

open

未解決として残っているもの

カバレッジ100%でも、抽出漏れは見えない
カバレッジの分母は「エージェントが抽出できたclaim」でしかない。抽出されなかった領域は、未学習としてすら現れず、満点の画面の裏に消える。 unknown unknowns を減らすために作った仕組みが、新しい unknown unknown を作る構造になっている。 分母の信頼性を別の軸（ファイル網羅率、未claim領域の明示など）で示す必要がある。
承認ゲートなしで、claimの品質下限をどう保つか
「怪しい」ボタンは、疑いを持てた人にしか押せない。もっともらしく間違ったclaimほど疑われずに残る。 抽出時にエージェント自身がどこまで自己検証するか（grepやテストで裏を取る、反例を探す）が実質的な品質の下限になる。
1問ずつの往復はターンを消費する
適応的な出題と引き換えに、待ち時間とコストが線形に増える。 選択式と場所当てはサーバ側で即採点できるので、往復が本当に必要なのは記述問題と次問の選択だけ。ここを設計で削れる余地がある。
新メンバーの初日、数百のclaimの前でどこから始めるか
claim集合はあるが .learning は空。推定理解度も出さない。トピック一覧だけでは入口が広すぎる。 既存開発者には自明な「まずここ」の順序を、共有側に何らかの形で持たせる必要があるかもしれない。
忘却をどう扱うか
陳腐化はコード変更で検出できるが、コードが変わらなくても人は忘れる。間隔反復を入れるかどうかは、定期実行の検討と一緒に決まる。
